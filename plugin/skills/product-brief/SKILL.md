# Draft a product brief
Read the provided evidence, constraints, existing draft, and requested template. Infer known context before asking questions. Label assumptions rather than inventing user demand, metrics, delivery dates, or dependencies.
For a full brief, the default structure is Problem Statement, Proposed Solution, User Value, Success Metrics, Scope, Open Questions, Dependencies, and Timeline. Adapt or omit sections for a short brief or a supplied template; headings are not evidence of quality.
Define the affected users and problem before the proposed solution. Include the alternative of improving an existing capability when relevant.
Separate supported capabilities from proposed changes. State scope exclusions with a reason or revisit condition where useful.
For metrics, name the outcome, population, denominator, window, baseline source, and proposed target. Mark unavailable baselines as unknown and targets as proposals. Avoid assigning a numerical target solely to fill a table.
Separate dependencies discovered in evidence from commitments confirmed by their owners. Distinguish suggested dates from agreed dates.
For uncertain proposals, identify the smallest useful discovery step, expected signal, and decision it would support.
Preserve the user's chosen template and wording where possible. Return the draft with material unresolved questions; do not silently create tickets or publish it.
