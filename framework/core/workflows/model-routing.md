# Choose a model for a task

Use when model choice creates a meaningful quality, latency, privacy or cost trade-off. This guide provides selection criteria, not a permanent ranking, price list or automatic routing service.

## Select against the actual work

- Routine extraction or bounded transformation: compare a lower-cost option with explicit completeness and fidelity checks.
- Ambiguous strategy, consequential reasoning or conflicting evidence: prioritize reasoning quality, source handling and uncertainty over speed.
- Tool-based execution: verify the model/runtime's ability to use the required tools and preserve instructions, not just its prose quality.
- Long tasks: keep a short durable handoff and selected sources; a larger context window is not a substitute for maintained context.
- Sensitive information: use the organization's approved model, data destinations and access controls. A task prompt does not authorize a new external processor.

Check the provider's current model documentation, runtime availability and prices when making a real choice. Use the exact model requested by the user. Do not rely on old aliases, internal labels, fixed cost-saving percentages or claims that a task is inherently reasoning-free.

## Compare realistically

Run a small representative task with observable quality criteria and a fixed source scope. Assess unsupported claims, missed records, tool failures, verification effort, latency and actual cost where available. A faster answer that requires substantial correction may be the worse choice. Record limits; one successful example is not a general benchmark.

Switch models at a coherent handoff when useful: goal, accepted decisions, evidence, remaining work and next action. Preserve existing approvals and source boundaries. Follow runtime-specific official guidance for selecting a model; this framework does not alter global defaults or implement an automatic fallback chain.
